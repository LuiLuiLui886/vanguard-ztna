Setelah mengikuti modul, peserta mampu:

2. Mengenal sistem dan identitas

VanGuard mengizinkan perangkat menjadi peer WireGuard setelah akun karyawan terautentikasi dan identitas perangkat lolos pemeriksaan. Sistem tidak mengubah kernel atau protokol WireGuard.

Urutan kerja:

Client membuat key sendiri → request publik → admin menerbitkan sertifikat/binding
Karyawan login → sesi akun → challenge → proof ditandatangani key perangkat
Server memeriksa sertifikat/CRL/proof/binding → ACCEPT → peer WireGuard aktif
Client membentuk tunnel → handshake → akses yang diizinkan → admission berkala

Enam pemeriksaan perangkat: signature X.509 terhadap Root CA, masa berlaku sertifikat, CRL terkini, serial tidak dicabut, bukti kepemilikan private key X.509, dan kecocokan sertifikat dengan public key WireGuard pada registry. Password karyawan yang benar tidak menggantikan pemeriksaan tersebut.

Jenis identitas Dipakai untuk Penyimpanan/penanggung jawab
Akun OS/console Masuk Ubuntu atau Windows Operator; inventaris privat host
Admin dashboard Mengelola akun, sertifikat dan audit Password + TOTP admin
Karyawan VPN Meminta sesi akses VPN Password karyawan dari admin
Identitas perangkat Membuktikan perangkat memiliki key yang terdaftar Private key tetap di client
Token antarlayanan Otorisasi API administrasi CA/server Berkas env privat layanan

TOTP admin berasal dari aplikasi authenticator yang telah didaftarkan. Dashboard memverifikasi kode enam digit; tidak menyediakan tombol untuk menampilkan kode login berjalan. Karyawan VPN tidak memakai TOTP admin untuk login.

Sesi karyawan berlaku delapan jam pada implementasi ini. Admission berkala memperbarui lease perangkat, tetapi tidak memperpanjang sesi karyawan. Ketika sesi habis, karyawan harus login lagi. Private key, token sesi, seed TOTP, dan password bukan lampiran laporan.

5.1 Siapkan host, enam guest, source dan SSH

5.3 Buat CA, trust dan sertifikat HTTPS

Bagian ini sudah mencakup generate CA. Untuk petunjuk lebih rinci per perintah, contoh transfer CSR/sertifikat melalui HOST, pemeriksaan CRL, backup dan diagnosis, baca panduan CA/PKI lengkap atau versi HTML panduan CA.

5.3.1 Apa yang dibuat dan mengapa diperlukan

CA (Certificate Authority) adalah penerbit sertifikat yang dipercaya lab. Sertifikat memuat identitas, public key, masa berlaku dan signature penerbit. Private key digunakan untuk menandatangani atau membuktikan kepemilikan identitas; sertifikat publik tidak berisi private key.

Artefak Fungsi Lokasi utama
Root private key Menandatangani sertifikat/CRL CA: /var/lib/vanguard/ca/private/root.key
Root certificate Trust anchor untuk memverifikasi penerbit CA: root.crt; salinan publik di layanan/client
HTTPS key + certificate Membuktikan identitas API CA/server/dashboard /etc/vanguard/tls.key dan tls.crt pada guest layanan
Device key + certificate Signature proof perangkat saat admission identity.key dan device.crt pada client
WireGuard keypair Identitas terpisah untuk tunnel WireGuard wg.key pada client; public key terikat di registry
CRL Daftar serial sertifikat yang dicabut CA: /var/lib/vanguard/ca/crl.pem

Alur sertifikat HTTPS: guest layanan membuat key dan CSR → CA menandatangani CSR → sertifikat kembali ke guest → guest menjalankan HTTPS. CSR adalah permintaan berisi public key dan identitas, bukan private key. Alur perangkat berbeda: client membuat request.json → admin mendaftarkan → CA menerbitkan device certificate → server menyimpan binding. Penerbitan sertifikat belum menjadi admission atau handshake VPN.

Parameter dari source 0.1.8: root RSA 3072/SHA256 berlaku3650 hari; HTTPS berlaku 365 hari dengan SAN IP dan serverAuth; perangkat P-256/clientAuth berlaku30 hari; CRL memiliki jendela1 jam dan dibuat baru pada setiap pengambilan melalui API. Masa berlaku dihitung sejak penerbitan, bukan diperbarui dengan restart VM. Root memiliki CA:true/pathlen:0; implementasi ini tidak memakai intermediate CA.

5.3.2 Pastikan ini CA baru, lalu jalankan init

Pada VM-CA, periksa dahulu:

sudo ls -la /var/lib/vanguard/ca
timedatectl status

Jika sudah ada openssl.cnf, root.crt, private/root.key atau state CA lain, jangan ulangi init atau menghapus berkas untuk memaksanya berhasil. Gunakan bagian verifikasi pada panduan CA. Pada lab yang ada sekarang, CA sudah dibuat.

VM-CA baru:

sudo -u vanguard /opt/vanguard/venv/bin/vanguard-ca init
sudo install -m 0644 /var/lib/vanguard/ca/root.crt /etc/vanguard/root.crt
openssl x509 -in /etc/vanguard/root.crt -noout -fingerprint -sha256

Perintah pertama membuat struktur CA, root key/certificate dan CRL awal. Target keluaran: CA initialized: /var/lib/vanguard/ca/root.crt. Perintah kedua menempatkan sertifikat root publik di path trust standar. Perintah ketiga menghasilkan fingerprint SHA256 yang perlu dicocokkan pada setiap salinan. CA already initialized; refusing to overwrite adalah perlindungan identitas lama, bukan instruksi menghapus CA.

Di balik init, aplikasi menjalankan OpenSSL dan menyiapkan index.txt, serial, crlnumber, newcerts serta konfigurasi penerbitan. Membuat file root.crt saja dengan perintah OpenSSL generik belum menghasilkan CA VanGuard yang lengkap. Key root tidak memakai passphrase dalam implementasi layanan ini, sehingga mode 0600, direktori 0700, akses VM dan backup privat harus dijaga.

5.3.3 Verifikasi root dan sebarkan trust publik

Di VM-CA:

openssl x509 -in /etc/vanguard/root.crt -noout -subject -issuer -dates
openssl x509 -in /etc/vanguard/root.crt -noout -ext basicConstraints,keyUsage
openssl verify -check_ss_sig -CAfile /etc/vanguard/root.crt /etc/vanguard/root.crt
sudo stat -c '%a %U:%G %n' /var/lib/vanguard/ca/private/root.key

Target: issuer/subject VanGuard Root CA, CA:TRUE/pathlen:0, penggunaan Certificate Sign/CRL Sign, verifikasi OK, key root 0600 milik akun CA. Mempercayai file root yang baru diterima tetap membutuhkan pembandingan fingerprint melalui sumber tepercaya; self-signature OK saja tidak membuktikan bahwa file tersebut berasal dari CA lab Anda.

Catat fingerprint. Salin hanya root.crt ke /etc/vanguard/root.crt pada Ubuntu lain dan cocokkan fingerprint. Root private key tetap di CA.

5.3.4 Buat key/CSR HTTPS pada tiap guest layanan

Pada masing-masing VM-CA, VM-SERVER, VM-ADMIN, buat key HTTPS lokal:

sudo openssl req -new -newkey rsa:3072 -nodes \
  -keyout /etc/vanguard/tls.key -out /etc/vanguard/tls.csr \
  -subj '/CN=VanGuard Service'
sudo chown root:vanguard /etc/vanguard/tls.key
sudo chmod 0640 /etc/vanguard/tls.key

Jalankan hanya jika tls.key belum ada. -newkey rsa:3072 membuat key baru, -nodes menghasilkan key tanpa enkripsi passphrase, -keyout menunjuk key rahasia, -out menunjuk CSR publik, dan -subj menentukan Common Name. Kesamaan CN contoh pada tiga layanan tidak berarti key-nya sama; setiap guest membuat key independen. Identitas alamat HTTPS ditentukan SAN IP saat signing. Hak root:vanguard 0640 membuat service dapat membaca key tanpa membukanya untuk seluruh pengguna guest.

5.3.5 Tandatangani CSR pada CA dan pasang hasilnya

Transfer CSR ke CA melalui SSH, dengan nama ca.csr, server.csr, admin.csr di /var/lib/vanguard/ca/requests/; direktori/CSR harus dapat dibaca akun service vanguard. Pada VM-CA, tandatangani sesuai IP:

sudo -u vanguard /opt/vanguard/venv/bin/vanguard-ca sign-tls \
  --csr /var/lib/vanguard/ca/requests/ca.csr --ip 192.168.100.10 \
  --out /var/lib/vanguard/ca/requests/ca.crt
sudo -u vanguard /opt/vanguard/venv/bin/vanguard-ca sign-tls \
  --csr /var/lib/vanguard/ca/requests/server.csr --ip 192.168.100.20 \
  --out /var/lib/vanguard/ca/requests/server.crt
sudo -u vanguard /opt/vanguard/venv/bin/vanguard-ca sign-tls \
  --csr /var/lib/vanguard/ca/requests/admin.csr --ip 192.168.100.40 \
  --out /var/lib/vanguard/ca/requests/admin.crt

Kembalikan sertifikat yang sesuai ke /etc/vanguard/tls.crt pada masing-masing guest dengan mode 0644. Pada setiap guest layanan, jalankan:

openssl verify -CAfile /etc/vanguard/root.crt /etc/vanguard/tls.crt

Target OK. Key HTTPS service tidak ditransfer ke CA. Simpan salinan root publik di host untuk trust browser dan pemeriksaan HTTPS.

Periksa juga tujuan dan alamat sertifikat. Contoh VM-SERVER:

openssl x509 -in /etc/vanguard/tls.crt -noout -ext subjectAltName,extendedKeyUsage
openssl verify -purpose sslserver -verify_ip 192.168.100.20 \
  -CAfile /etc/vanguard/root.crt /etc/vanguard/tls.crt

Target SAN IP .20, TLS Web Server Authentication dan OK. Untuk CA gunakan .10, untuk ADMIN .40. Sertifikat layanan tidak dipakai sebagai sertifikat perangkat; validator perangkat mengharuskan clientAuth/P-256, bukan serverAuth. Lanjutkan pengisian token di bab 5.4 sebelum menyalakan layanan pada bab 5.5.

5.3.6 Sertifikat perangkat, CRL dan pencabutan

Sertifikat perangkat dibuat melalui workflow bab 6, bukan sign-tls. CA memeriksa signature CSR, public key P-256 dan CN yang cocok device ID. Dashboard meminta issuance ke CA, mendaftarkan sertifikat/public key WireGuard/ alamat tunnel pada server, lalu mengikat akun karyawan. Client harus login dan menjalani challenge/proof sebelum server memasang peer.

Saat admin mencabut perangkat, workflow menonaktifkan akses dan meminta CA mencabut serial sertifikat. CA memperbarui index dan menandatangani CRL baru. Jangan mengedit CRL/serial manual untuk mencabut perangkat; gunakan dashboard dan tunggu status revoked. Panduan CA menjelaskan pemeriksaan signature, lastUpdate/nextUpdate serta verifikasi sertifikat memakai -crl_check.

Renewal admission tidak memperpanjang sertifikat30 hari. Jika sertifikat habis atau dicabut, belum tersedia renewal sertifikat otomatis pada sistem ini; operator perlu workflow identitas baru yang terkontrol. Jangan membuat CA baru untuk mengatasi satu sertifikat client yang expired.

5.4 Konfigurasi token dan akun admin awal

Buat tiga nilai acak independen dengan openssl rand -hex 32 dalam terminal privat. Isi template env menggunakan sudoedit; jangan menaruh nilai literal di command history atau dokumen. Catat lokasi dan nilai hanya pada inventaris privat operator.

Variabel Lokasi yang menerima nilai sama
VANGUARD_CA_TOKEN ca.env di CA dan admin.env di ADMIN
VANGUARD_SERVER_TOKEN server.env di SERVER dan admin.env di ADMIN
VANGUARD_SESSION_SECRET admin.env di ADMIN; nilai ketiga yang independen

Semua file berada pada /etc/vanguard/, owner root:root, mode0600. Pastikan URL CA/server dan path sertifikat pada template sesuai topologi. Pada VM-ADMIN baru, buat satu admin melalui prompt:

sudo -u vanguard /opt/vanguard/venv/bin/vanguard-admin --username NAMA_ADMIN_BARU

Password minimal 12 karakter, diketik dua kali. Daftarkan URI TOTP yang ditampilkan di terminal privat ke authenticator dan konfirmasi kode. Jangan membuat ulang akun admin utama hanya karena sesi login habis.

5.5 Firewall dan layanan

Jalur yang perlu diizinkan: CA8080 dari SERVER/ADMIN; SERVER8081 dari kedua client, ADMIN dan ATTACKER; UDP 51820 dari kedua client dan ATTACKER; ADMIN5000 dari host. SSH guest hanya dari manajemen. ICMP10.8.0.1 dari.2/.4 harus masuk lewat wg0; trafik ke alamat tunnel yang datang langsung dari LAN ditolak.

Pasang nftables pada Ubuntu yang akan diberi aturan. Salin deploy/firewall.py ke /opt/vanguard/firewall.py pada guest. Di guest masing-masing jalankan sudo python3 /opt/vanguard/firewall.py ROLE --management-ip 192.168.100.1, dengan ROLE ca, server, client, admin, atau attacker. Khusus SERVER:

sudo python3 /opt/vanguard/firewall.py server \
  --management-ip 192.168.100.1 --windows-client

Simpan ruleset sebelum perubahan. Skrip memasang timer rollback120 detik. Buka koneksi SSH baru dan periksa sudo systemctl is-active vanguard-firewall; baru hentikan vanguard-firewall-rollback.timer pada guest itu. Jika SSH gagal, gunakan console dan periksa rollback; jangan menandai firewall siap.

Mulai layanan sesuai guest:

# VM-CA
sudo systemctl enable --now vanguard-ca
# VM-SERVER
sudo systemctl enable wg-quick@wg0 vanguard-daemon vanguard-server
sudo systemctl start vanguard-server
sudo wg show wg0 peers
# VM-ADMIN
sudo systemctl enable --now vanguard-admin

Pada instalasi baru, daftar peer harus kosong sebelum admission client. Setelah HTTPS sehat, lanjutkan bab 6. Jangan menambahkan peer manual untuk mempercepat demo.

5.6 Pasang aplikasi Windows baru

  1. Pasang Python 3.12 atau lebih baru dan WireGuard for Windows dari penerbit resmi; periksa signature installer. Jangan menonaktifkan Windows Firewall.
  2. Atur NIC ke 192.168.100.60/24, gateway/DNS.1, waktu Jakarta. Pastikan koneksi HTTPS ke server tersedia dan sertifikat root cocok fingerprint operator.
  3. Build wheel source di HOST dengan .venv/bin/python -m pip wheel --no-deps --wheel-dir dist ., lalu transfer wheel0.1.8 dan deploy/constraints.txt ke folder staging privat guest.
  4. Pada PowerShell Administrator, buat virtualenv; sesuaikan path Python dan wheel:
& 'C:\Program Files\Python313\python.exe' -m venv C:\ProgramData\VanGuard\venv
$py = 'C:\ProgramData\VanGuard\venv\Scripts\python.exe'
& $py -m pip install -c C:\VG-Staging\constraints.txt C:\VG-Staging\vanguard_ztna-0.1.8-py3-none-any.whl
& $py -m pip check
& $py -m vanguard.client --help

Python313 adalah lokasi instalasi yang dibuktikan pada guest ini; ganti bila berbeda. Instalasi pip di atas membutuhkan akses dependensi, atau wheelhouse terverifikasi yang disiapkan teknisi. Paket0.1.8 membutuhkan pywin32 di Windows. Jika installer memakai autologon/unattend, teknisi harus membersihkan secret setup dan mengeluarkan media seed sesudah selesai. Lanjut bab 6 untuk perangkat yang belum diinisialisasi. SSH Windows opsional untuk pemeliharaan; pemakaian normal bisa melalui console, dengan hak Administrator untuk mengelola tunnel.

6. Admin: menyiapkan akun dan perangkat

6.1 Login dashboard

  1. Di browser HOST buka https://192.168.100.40:5000 dengan trust CA yang benar.
  2. Masukkan username/password admin dashboard dan kode TOTP dari authenticator.
  3. Klik Masuk. Halaman Perangkat & admission harus terbuka.
  4. Periksa Kesehatan layanan: CA dan Server tersedia.

Di lab terpasang, informasi aktivasi privat berada di state/deployment/aktivasi-admin.html. QR/seed hanya untuk pemilik akun. TOTP memakai waktu, SHA-1, enam digit,30 detik. Kode yang sudah dipakai tidak bisa dipakai untuk login kedua; tunggu kode berikutnya. Setelah lima kegagalan, tunggu lima menit. Sesi dashboard sekitar 30 menit.

6.2 Buat akun karyawan

Pada Akun karyawan, isi username unik dan password awal minimal 12 karakter, lalu klik Buat akun karyawan. Serahkan kredensial melalui kanal privat dan catat pada inventaris lokal operator. Akun Ubuntu dan Windows lab sudah ada; gunakan akun yang terikat pada perangkat masing-masing. Belum ada fitur reset password mandiri atau aktivasi ulang akun yang dinonaktifkan.

6.3 Buat request hanya pada client baru

Ubuntu baru, pada VM-CLIENT:

sudo /opt/vanguard/venv/bin/vanguard-client init --device-id vm-client

Hasilnya /var/lib/vanguard/client/request.json. Default alamat Ubuntu.2. Pada Windows baru, PowerShell Administrator:

$py = 'C:\ProgramData\VanGuard\venv\Scripts\python.exe'
& $py -m vanguard.client init --device-id vm-client-windows --tunnel-ip 10.8.0.4

Hasilnya C:\ProgramData\VanGuard\client\request.json. Direktori identitas dilindungi ACL SYSTEM/Administrators. identity.key dan wg.key tetap di guest. Salin request.json saja ke host operator melalui transfer tepercaya. Pada guest yang sudah terdaftar jangan mengulang init atau mengganti request.

6.4 Daftar, unduh dan pasang sertifikat

  1. Pada Registrasi perangkat, pilih request JSON yang sesuai.
  2. Isi Nama perangkat, Departemen, Pemilik, dan Platform.
  3. Pilih akun karyawan yang benar. Binding akun-perangkat tidak dapat diganti hanya dengan mengedit metadata; periksa pilihan sebelum mengirim.
  4. Klik Terbitkan sertifikat & daftarkan binding.
  5. Pastikan workflow registered. Peer perangkat baru harus belum aktif.
  6. Klik Unduh bundle onboarding atau Unduh sertifikat pada baris tersebut. Bundle berisi device.crt, root.crt, manifest dan petunjuk; tidak berisi key.
  7. Cocokkan device ID, public key/binding pada manifest dan fingerprint root dengan referensi operator sebelum mengimpor. Pasang hanya pada client pembuat CSR.

Pada Ubuntu, salin sertifikat ke staging guest, kemudian:

sudo install -m 0600 /PATH/STAGING/device.crt /var/lib/vanguard/client/device.crt

Trust Ubuntu di /etc/vanguard/root.crt sudah disiapkan pada instalasi layanan. Pada PowerShell Administrator Windows, setelah bundle publik diekstrak ke staging:

Copy-Item C:\VG-Staging\device.crt C:\ProgramData\VanGuard\client\device.crt
Copy-Item C:\VG-Staging\root.crt C:\ProgramData\VanGuard\client\root.crt

Jika file tujuan sudah ada, teknisi membandingkan identitasnya dahulu; jangan menimpa sertifikat utama dengan hasil latihan. Client memeriksa kesesuaian sertifikat dengan key lokal saat admission. Registrasi dan unduhan bundle belum mengaktifkan tunnel. Workflow tertahan dilanjutkan dengan Ulangi workflow setelah dependency pulih, bukan mengirim registrasi duplikat.

7. Karyawan Ubuntu: login dan memakai VPN

Prasyarat: perangkat sudah registered, sertifikat/root terpasang, akun terikat dan aktif. Di HOST masuk ke VM-CLIENT:

ssh -F ~/.ssh/vanguard_lab_config 192.168.100.30

Di VM-CLIENT masukkan username karyawan dari inventaris privat:

sudo /opt/vanguard/venv/bin/vanguard-client login --username USERNAME_KARYAWAN_UBUNTU
sudo systemctl restart vanguard-client
sudo systemctl status vanguard-client --no-pager
ping -c 3 -W 2 10.8.0.1
sudo wg show wg0

Password diminta tersembunyi. Login menghasilkan masa kedaluwarsa; client menyimpan token privat, bukan password. Target: ping berhasil, handshake ada, dan dashboard menunjukkan peer perangkat aktif. Jika delapan jam habis, login kembali dan restart service. Logout dashboard tidak mengakhiri VPN ini.

Untuk instalasi Ubuntu baru, service membutuhkan /etc/vanguard/client.env dengan VANGUARD_SERVER_WG_PUBLIC_KEY berisi public key dari /etc/vanguard/server-wg.pub pada SERVER. Teknisi memasangnya root:root0600 melalui editor lalu sudo systemctl enable vanguard-client. Installer saja belum mengisi nilai ini. Jangan memakai private key server.

Alternatif foreground untuk teknisi: stop service terlebih dahulu, kemudian jalankan sudo /opt/vanguard/venv/bin/vanguard-client connect --server-key 'PUBLIC_KEY_SERVER'. Jangan menjalankan service dan foreground bersamaan.

8. Karyawan Windows: dari login desktop sampai disconnect

  1. Buka console VM-CLIENT-WINDOWS melalui virt-viewer/virt-manager.
  2. Masuk memakai username/password console Windows pada kartu lokal host.
  3. Buka Start, cari PowerShell, pilih Run as administrator, setujui UAC.
  4. Pastikan server, CA dan jaringan siap. Lab Windows sudah memiliki sertifikat dan key; tidak perlu init atau pendaftaran ulang.
  5. Jalankan:
$py = 'C:\ProgramData\VanGuard\venv\Scripts\python.exe'
& $py -m vanguard.client login --username USERNAME_KARYAWAN_WINDOWS
& $py -m vanguard.client connect --server-key 'PUBLIC_KEY_SERVER'

Username/password langkah5 adalah akun VPN Windows, berbeda dari akun desktop langkah2. Public key server diperoleh operator melalui SSH terverifikasi ke SERVER, dengan sudo cat /etc/vanguard/server-wg.pub. Ini nilai publik yang boleh diberikan kepada karyawan; bukan isi /etc/wireguard/wg0.conf.

Target terminal: Admitted; tunnel up. Renewing admission until stopped. Biarkan terminal ini berjalan. Pada PowerShell Administrator kedua:

ping -n 3 10.8.0.1
& 'C:\Program Files\WireGuard\wg.exe' show vanguard-client
sc.exe qc 'WireGuardTunnel$vanguard-client'

Target: balasan ping, latest handshake, dan start type DEMAND_START. Pada dashboard cari vm-client-windows dengan tunnel.4 dan peer aktif. Jangan menambah tunnel manual lewat GUI WireGuard untuk melewati admission.

Untuk selesai, tekan Ctrl+C di terminal connect, lalu periksa:

sc.exe query 'WireGuardTunnel$vanguard-client'
Test-Path C:\ProgramData\VanGuard\client\vanguard-client.conf

Setelah cleanup selesai, query service menghasilkan1060/tidak ditemukan dan Test-Path False. Versi 0.1.8 menunggu penghapusan service hingga 15 detik; bila tidak bisa memastikan cleanup, config dipertahankan agar bisa diperiksa. Private key dan sertifikat tetap disimpan untuk koneksi berikutnya.

Windows tidak otomatis menyalakan tunnel ketika reboot. Buka PowerShell admin dan jalankan connect lagi; login ulang jika sesi sudah expired. Satu siklus renewal otomatis sudah dibuktikan, bukan uji kestabilan berjam-jam.

9. Memastikan sistem sudah dapat digunakan

Gunakan daftar penerimaan berikut. Isi hasil aktual dan tanggal, bukan menyalin PASS dari hasil historis.

Pemeriksaan Bukti yang dicatat Kriteria lulus
Mesin tersedia Daftar VM dan tanggal VM yang dipakai running dan selesai boot
Kepercayaan HTTPS Fingerprint publik dan health Root cocok; tidak menonaktifkan TLS
Admin Login TOTP, halaman dashboard Masuk dengan kode yang sah; CA/Server tersedia

Di SERVER gunakan sudo wg show wg0 atau sudo wg show wg0 peers. Jangan gunakan format dump untuk laporan, karena dapat memuat private key. Peer server bisa bertahan hingga lease habis sesudah client berhenti; ini berbeda dari service tunnel lokal yang sudah dibersihkan. Pencabutan/disable menjalankan penghapusan peer sesuai workflow server.

Runner scripts/health_lab.py bergantung pada client Ubuntu utama yang aktif; bukan tes Windows. Bila diperlukan oleh teknisi di HOST:

module_run="state/deployment/module-$(date +%Y%m%d-%H%M%S)"
.venv/bin/python scripts/health_lab.py state/lab/inventory.json \
  --state "$module_run/health" --samples 3 --interval 10

Gunakan direktori baru per run. Jika hanya Windows yang aktif, periksa melalui bab 8 dan SERVER; jangan mengartikan health runner Ubuntu gagal sebagai bukti tunnel Windows gagal.

10. Admin: aktivitas, arsip, dan penghentian akses

10.1 Mencari tindakan berdasarkan waktu

  1. Klik Aktivitas admin.
  2. Pilih tanggal mulai/akhir dalam WIB, lalu filter pelaku, ID perangkat atau jenis tindakan. Tanggal akhir mencakup satu hari penuh.
  3. Klik Tampilkan. Telusuri halaman berikutnya bila lebih dari50 baris.
  4. Periksa jam-menit-detik, pelaku, tindakan dan keterangan Indonesia.

Satu tindakan dapat memiliki tahap diminta, gagal, retry dan selesai. Aktivitas keamanan server berasal dari proses VPN otomatis; jangan menyamakan aktor otomatis dengan admin yang sedang login. Waktu sumber disimpan Unix/UTC, sedangkan tampilan dan CSV menggunakan WIB.

10.2 Menyimpan arsip yang dapat diverifikasi

  1. Setelah filter sesuai, klik Simpan arsip aktivitas.
  2. Snapshot memuat seluruh hasil filter, bukan hanya halaman yang sedang tampil. Batasnya10.000 catatan dan8 MiB sebelum ZIP; persempit filter jika melewati batas.
  3. Buka Arsip, periksa pembuat, waktu, jumlah dan filter; unduh ZIP.
  4. ZIP berisi aktivitas.csv, aktivitas.json, manifest.json, PETUNJUK.txt.
  5. Di HOST jalankan sha256sum /PATH/ARSIP.zip dan cocokkan dengan checksum di dashboard. Manifest mencatat checksum CSV/JSON untuk verifikasi isi.
  6. Simpan ZIP di folder privat operator dan catat path pada lembar praktikum.

Arsip tidak menghapus log asal. Arsip tersimpan dalam database VM-ADMIN, sehingga backup database tetap diperlukan. Checksum bukan tanda tangan digital dan tidak menjamin ketahanan terhadap root VM yang dapat mengubah database.

10.3 Mencabut akses

Pada perangkat yang memang hendak dihentikan, pilih alasan dan klik Cabut akses & sertifikat. Tunggu status revoked, periksa peer hilang dan admission ulang ditolak. Status revoking belum berarti proses selesai; pulihkan dependency lalu pilih Ulangi workflow.

Nonaktifkan akun karyawan membatalkan sesi dan menghapus peer terkait, tetapi tidak otomatis mencabut sertifikat. Identitas yang dicabut memerlukan device ID dan key baru untuk pemakaian berikutnya; bukan edit metadata. Gunakan identitas disposable untuk latihan, bukan vm-client atau vm-client-windows yang sedang dipakai.

11. Praktikum dan penilaian

Praktikum dilakukan pada lab yang diotorisasi. Alokasi waktu berikut hanya perkiraan untuk sesi pembelajaran, bukan hasil benchmark.

Praktikum Waktu Tugas dan keluaran
A: orientasi 20 menit Gambar enam node dan jelaskan tiga jenis akun
B: kesiapan 20 menit Periksa VM, waktu, trust dan health; catat kendala
C: pemakaian 30 menit Login client yang dipilih, handshake/ping, disconnect
D: administrator 25 menit Login TOTP, cari aktivitas WIB, buat/cek arsip
E: enrollment latihan 45 menit Identitas disposable → registered → admission → revoke → cleanup

Praktikum E memakai prosedur terpisah pada tutorial bab 7. Prosedur tersebut mengikuti client Ubuntu 0.1.5 yang terpasang dan memakai alamat eksperimen.3. Pastikan tidak ada eksperimen lain aktif. Latihan admit tidak membuktikan trafik; pengujian ping tetap dilakukan pada client utama. Jangan menyalin key ke attacker.

Contoh penilaian: kesiapan20 poin, penjelasan akun/admission20, koneksi dan disconnect30, audit/arsip20, pencatatan aman10. Lulus minimal 80/100 dan tidak memasukkan kredensial/private key pada bukti. Rubrik ini usulan pembelajaran.

Pertanyaan evaluasi:

  1. Mengapa password karyawan yang benar belum cukup untuk mendapatkan tunnel?
  2. Apa perbedaan registered, peer aktif, handshake dan ping berhasil?
  3. Mengapa login karyawan harus diulang meskipun renewal perangkat berjalan?
  4. Apa perbedaan disable akun, revoke sertifikat dan logout dashboard?
  5. Mengapa checksum arsip belum membuktikan bahwa root VM tidak mengubah isinya?

Jawaban inti: akun dan perangkat diperiksa terpisah; registry bukan akses; lease dibatasi sesi login; tindakan penghentian memiliki sasaran berbeda; checksum tidak memiliki penandatangan independen.

12. Mengakhiri sesi dan mematikan lab

  1. Karyawan Windows: Ctrl+C pada connect dan periksa cleanup sesuai bab 8.
  2. Karyawan Ubuntu: sudo systemctl stop vanguard-client; pastikan wg0 tidak aktif pada client. Perintah ini tidak mematikan interface server.
  3. Admin: simpan arsip bila perlu, kemudian klik Keluar.
  4. Jika seluruh lab hendak dimatikan, dari HOST kirim shutdown normal:
virsh -c qemu:///system shutdown VM-CLIENT-WINDOWS
virsh -c qemu:///system shutdown VM-CLIENT
virsh -c qemu:///system shutdown VM-ATTACKER
virsh -c qemu:///system shutdown VM-ADMIN
virsh -c qemu:///system shutdown VM-SERVER
virsh -c qemu:///system shutdown VM-CA
virsh -c qemu:///system list --all

Kirim hanya pada VM running. Tunggu seluruh target shut off sebelum mematikan host. Respons shutdown sukses berarti permintaan terkirim, bukan guest pasti sudah mati. Jika Windows tidak merespons ACPI, gunakan Start → Power → Shut down di console. Hindari force-off saat CA menulis state.

Backup oleh teknisi: hentikan layanan penulis terkait atau gunakan backup SQLite konsisten, lalu simpan konfigurasi /etc/vanguard, state /var/lib/vanguard, WireGuard /etc/wireguard dan versi paket sebelumnya di lokasi privat. Backup CA berisi key sensitif; batasi akses. Pemulihan tidak boleh mengembalikan index/CRL lama sehingga sertifikat tercabut menjadi berlaku kembali. Catat tanggal, hash backup, layanan yang dihentikan/dimulai, dan pemeriksaan setelah pemulihan.

Untuk diagnosis layanan Ubuntu, gunakan sudo journalctl -u NAMA_UNIT -n 50 --no-pager. Tinjau hasil secara privat sebelum menyalin ke laporan. Pemulihan counter CA15 Oktober menjaga signature, monotonic counter dan seluruh revocation; ini tindakan teknisi berdasarkan bukti, bukan perintah rutin pengguna.
